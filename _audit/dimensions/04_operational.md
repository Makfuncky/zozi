## Overall

### Problem(s)
1. **Gunicorn misconfiguration** (`OP-001`): Production server process lacks worker count, graceful timeout, max_requests, and log rotation — risks OOM, ungraceful restarts, and log sprawl.
2. **Missing runbooks** (`OP-002`): No per-alert operational runbooks exist; incident response is ad-hoc.
3. **Migration-on-deploy ordering** (`OP-003`): Migrations run after deploy but before health check; new replicas may serve stale schema during rolling deploy.
4. **Financial job idempotency gap** (`OP-004`): `run_payout_sweep` lacks idempotency key; retry may cause duplicate financial transactions.
5. **R2 missing from health checks** (`OP-005`): `/health/deps` and `/health/ready` do not check R2 object storage dependency.
6. **Celery signal handlers incomplete** (`OP-006`): Worker lifecycle hooks log state but do not initialize/close DB connections or dispose SQLAlchemy engines.
7. **No application-level log rotation** (`OP-007`): Only Docker json-file driver configured; no structured JSON log output from gunicorn.
8. **No graceful shutdown flags** (`OP-008`): Gunicorn lacks `--graceful-timeout` and `--keep-alive`; workers killed abruptly during deploys.
9. **Missing `event_workers.py` module** (`OP-009`): `jobs.event_workers` listed in Celery `include` and `autodiscover_tasks` but file does not exist; worker fails to start with ImportError.
10. **6 mandatory scheduled jobs absent** (`OP-010`): `news_ingester`, `auto_document_expiry`, `facet_count_refresh`, `ai_embeddings_sync`, `escalation_engine`, `kpi_watchdog` have no beat entries; critical automated processes never execute.
11. **Bank statement importer unscheduled** (`OP-011`): `bank_statement_importer` task is registered but not in `beat_schedule`; no automatic execution.
12. **Celery broker URL scheme unvalidated** (`OP-012`): `celery_broker_url` / `celery_result_backend` are checked only for non-empty in production; no `valkey://` scheme enforcement.
13. **Worker concurrency unbounded** (`OP-013`): Only `task_concurrency=4` is set; no `worker_concurrency` configured, risking resource exhaustion on VPS.
14. **Beat schedule duplicate entries** (`OP-014`): `auto-payout-sweep` + `auto-payout-sweep-daily` and `finance-reconciliation` + `finance-reconciliation-cron` have overlapping schedules; risk of double-execution.
15. **No task queue depth monitoring** (`OP-015`): Celery queues lack depth metrics and alerts; queue buildup goes undetected.
16. **APScheduler not wired into lifespan** (`OP-016`): `start_background_jobs()` exists in governance command center but is never imported or called from `_startup_background_jobs()`; Command Center cache and finance cycles never start automatically.
17. **No per-task retry override for financial jobs** (`OP-017`): Payout and finance tasks rely on global Celery retry defaults; no explicit idempotent retry policies configured.

### Solution(s)
1. Add gunicorn config file with `workers = min(2 * cpu_count + 1, 8)`, `graceful-timeout = 30`, `max-requests = 1000`, `max-requests-jitter = 50`, and structured JSON logging.
2. Create `docs/runbooks/` with one file per alert category: `payout_failure.md`, `payment_gateway_down.md`, `valkey_unavailable.md`, `database_connection_failed.md`, `high_error_rate.md`, `celery_worker_down.md`.
3. In `deploy.yml`, run `alembic upgrade head` before `railway up`, or adopt blue/green deploy with migration gate.
4. Add `idempotency_key` parameter to `run_payout_sweep` and store processed keys in Valkey with 24h TTL.
5. Add R2 health check to `/health/deps` and `/health/ready` using `providers/storage/r2.py` `health_check()`.
6. Implement DB connection cleanup and worker state logging in `init_worker` and `shutdown_worker` signal handlers.
7. Configure gunicorn log config to output structured JSON via structlog with rotation.
8. Add `--graceful-timeout 30 --keep-alive 5` to gunicorn CMD in `Dockerfile.prod`.
9. Create `backend/jobs/event_workers.py` with registered tasks, or remove all `jobs.event_workers` references from `include` and `autodiscover_tasks` in `celery_app.py`.
10. Add missing 6 jobs to `beat_schedule` with appropriate schedules; implement task bodies if they do not exist.
11. Add `bank-statement-importer` entry to `beat_schedule` with daily cadence, or document external trigger mechanism.
12. Add `valkey://` scheme validation for `celery_broker_url` and `celery_result_backend` in production/staging validators in `config.py`.
13. Set `worker_concurrency` in `celery_app.conf.update()` to match VPS capacity (e.g. 2-4).
14. Remove duplicate beat entries (`auto-payout-sweep-daily`, `finance-reconciliation-cron`) or consolidate into single scheduled tasks.
15. Add Celery queue length metrics to Prometheus and create alerts for queue depth exceeding threshold.
16. Import and call `start_background_jobs()` from `domains.governance.services.command_center.background` in `_startup_background_jobs()` and return stopper for shutdown.
17. Add per-task retry annotations for payout and finance tasks with explicit `max_retries=1` and `retry_delay=300`.

### Suggestion(s)
1. Adopt a gunicorn config file (`gunicorn.conf.py`) rather than inline flags for maintainability.
2. Add automated runbook tests that verify each runbook has a corresponding alert rule in the monitoring system.
3. Consider adding a `pre-deploy` job in CI that runs migrations against a staging clone before promoting to production.
4. Audit `jobs/celery_app.py` `include` list against actual filesystem to prevent drift between registered and existing modules.
5. Document all beat schedule jobs in a central registry (`docs/jobs/schedule.md`) for ops visibility.
6. Add Celery Flower or alternative monitoring UI for real-time task status and queue depth visibility.
7. Add a CI lint rule that fails if `beat_schedule` contains duplicate keys or overlapping cron patterns.
