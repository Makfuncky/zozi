### 📜 2. The Golden Rules of Webhook Security
To defeat these threats, the Zozi backend must enforce three immutable rules for every incoming webhook:
1. **Never Parse Before Verifying:** You must read the **RAW BYTE BODY** (`await request.body()`) directly from the HTTP stream. If you use `await request.json()`, Python's JSON parser will reformat the string, instantly breaking the HMAC signature.
2. **Constant-Time Comparison:** When comparing the calculated hash with the gateway's hash, you must use `hmac.compare_digest()`. Standard `==` comparison is vulnerable to "Timing Attacks" where hackers measure microsecond differences in server response times to guess the hash character-by-character.
3. **Strict Idempotency:** Every gateway assigns a unique `event_id` to every webhook. The system must record this ID in the database *inside the exact same transaction* as the order update.

#### The Tap HMAC-SHA256 Verifier

```python
import hashlib
import hmac
import logging

logger = logging.getLogger(__name__)

def verify_tap_signature(raw_body: bytes, signature_header: str, secret: str) -> bool:
    """
    Constant-time HMAC-SHA256 verification for Tap Payments.
    """
    if not signature_header or not secret:
        return False
        
    # 1. Calculate expected hash from raw bytes
    expected_hash = hmac.new(
        secret.encode('utf-8'),
        raw_body,
        hashlib.sha256
    ).hexdigest()
    
    # 2. Constant-time comparison (Prevents Timing Attacks)
    is_valid = hmac.compare_digest(expected_hash, signature_header)
    
    if not is_valid:
        logger.warning(f"🚨 TAP WEBHOOK SIGNATURE MISMATCH. Expected: {expected_hash[:10]}... Got: {signature_header[:10]}...")
        
    return is_valid
```

```python
router = APIRouter()

@router.post("/webhooks/{provider_code}")
async def handle_payment_webhook(
    provider_code: str, 
    request: Request, 
    db: Session = Depends(get_db)
):

    raw_body = await request.body()

    if not is_valid:

    event_data = adapter.parse_webhook_payload(raw_body)
    event_id = event_data.get("event_id")

    except Exception as e:

        logger.exception(f"Webhook processing failed for {provider_code} event {event_id}")
```

### How It Works Together:

2. **ModSecurity** inspects the request against 200+ OWASP rules. If malicious, return `403` immediately.

**Result:** Malicious bots, scrapers, and brute-force attackers are stopped at the door. Only legitimate, encrypted, rate-limited traffic reaches your application.

## 🧩 How the 5 Layers Work Together: A Real-World Attack Scenario

**Attack:** A malicious supplier tries to access another supplier's payout data.

1. **Layer 1 (Network):** The request passes ModSecurity and rate limits (it's a valid HTTPS request from a known IP).
2. **Layer 2 (Application):** The JWT is valid, but the Row-Level Security middleware injects `WHERE supplier_id = :current_user_id`. The query returns no results. The API returns `404 Not Found` (not `403`, to avoid confirming the existence of the data).
3. **Layer 3 (Data):** Even if the attacker somehow bypassed Layer 2, the payout data is encrypted at rest. Without the application's decryption key (stored in Vault), the data is unreadable.
4. **Layer 4 (Behavioral):** The system notices the supplier is querying payout endpoints they never use. Anomaly score increases. The next request requires step-up authentication.
5. **Layer 5 (Audit):** The attempt is logged to the immutable audit table. The security team receives an alert: "Supplier #123 attempted to access unauthorized payout data." The supplier's account is automatically flagged for review.

**Result:** The attack fails at Layer 2, is detected at Layer 4, and is forensically recorded at Layer 5. The system is stronger for having detected the attempt.

## ⚙️ 3. Core Security Engines (Detailed Logic & Design)

### Engine A: Row-Level Security (RLS) & Country Isolation
*Goal: Ensure a `country_manager` can never see or modify data outside their assigned territory, even via direct API manipulation.*

1. **Context Injection Middleware:** Intercepts the JWT, queries a highly-cached Redis graph for the user's `Active Country Scope` (e.g., `['OM', 'AE']`), and attaches it to the Request State. Global Admins receive an `UNRESTRICTED` scope.
2. **The SQLAlchemy "Ghost Filter":** Utilizes SQLAlchemy global execution events. Every `SELECT`, `UPDATE`, or `DELETE` against a "Country-Aware" model is intercepted. The ORM invisibly injects `WHERE country_code IN (...)` into the SQL. If a background task lacks a security context, the ORM throws a fatal exception.
3. **Cross-Border Split Scope:** If an Omani customer buys from a Saudi supplier, PII is locked to the Omani privacy vault, while the Order record is tagged with the Saudi operating country for tax/logistics.
4. **The "Ghost Record" Protocol:** If a restricted user requests an Order ID from another country, the system returns `404 Not Found` (not `403 Forbidden`), making the existence of the data mathematically opaque to attackers.

### Engine B: Cryptographic Webhook & Treasury Verification
*Goal: Make the Payment Orchestrator immune to spoofing, tampering, and replay attacks.*

1. **Raw Byte Ingestion:** The router reads `await request.body()` directly. JSON parsing is strictly forbidden before verification to prevent byte-structure mutation.
2. **Gateway Matrix & Constant-Time Math:**
   * *Stripe:* Uses SDK `construct_event`.
   * *Tap/PayTabs:* Calculates `hmac.new(secret, raw_body, sha256)` and compares using `hmac.compare_digest()` to prevent timing attacks.
   * *PayPal:* Server-to-server POST to `/v1/notifications/verify-webhook-signature`.
3. **Anti-Replay & Idempotency Gate:** Validates timestamp (rejects if > 5 mins old). Queries `ProcessedWebhookEvent` for the gateway's `event_id`. If found, returns `200 OK` immediately to stop gateway retries.
4. **Treasury Mapping:** Inside a single DB transaction: Updates Order status $\rightarrow$ Triggers `TreasuryService.post_journal_entry()` (Debit Gateway Clearing, Credit Deferred Revenue) $\rightarrow$ Inserts `event_id`.
5. **Zero-Downtime Secret Rotation:** The DB stores an array of active webhook secrets. The backend tries the new secret first, falling back to the old one, allowing seamless rotation.
6. **Ghost Order Honeypot:** A nightly cron joins `Orders` to `ProcessedWebhookEvent`. If an order is marked "Paid" but lacks a valid webhook event, a Critical Fraud Alert is triggered.

### Engine C: Zero-Trust IAM, 2FA & Maker-Checker Protocols
*Goal: Eliminate insider threats, credential stuffing, and unauthorized financial disbursements.*

1. **Device Fingerprinting & Binding:** JWTs are cryptographically bound to a SHA-256 hash of the device's Canvas, WebGL, Timezone, and IP subnet. Token usage from a new device triggers an immediate lock.
2. **Impossible Travel Detection:** Compares login geolocation against previous sessions. Muscat at 09:00 + London at 11:00 = Account Lock + Tier 3 Alert.
3. **IP Risk Scoring Engine:** Assigns points (New Location +10, VPN/Proxy +15, Blacklisted IP +50). Scores >40 require Step-Up Authentication (TOTP); >60 triggers auto-block.
4. **Financial Maker-Checker (Four-Eyes):** 
   * *Creator (Finance 1):* Drafts payout batch $\rightarrow$ Enters TOTP.
   * *Reviewer (Finance 2):* Audits batch $\rightarrow$ Enters TOTP $\rightarrow$ Approves.
   * *Approver (Finance Head):* Final validation $\rightarrow$ Enters TOTP $\rightarrow$ Releases funds via Payment Orchestrator.

### Engine D: The Anti-AI & Anti-Scraping Gauntlet
*Goal: Neutralize LLM training bots, headless browsers, and competitor scrapers without paid WAFs.*

1. **Wasm Proof of Humanity:** Next.js loads an obfuscated WebAssembly module that monitors mouse entropy and scroll physics. It generates a cryptographic token every 10 seconds. FastAPI drops requests lacking this chaotic human signature.
