### 🛠️ Phase 5: Standardized SQLAlchemy Mixins

Instead of manually typing `created_at`, `is_deleted`, etc., on every single table, we will create reusable Mixins. Any model that inherits from these will automatically get the correct columns and indexes.

#### 1. Create the Mixins File
Create a new file at **`backend/db/mixins.py`** and paste this exact code. It uses modern SQLAlchemy 2.0 syntax.

```python
from datetime import datetime
from typing import Optional
from sqlalchemy import Boolean, DateTime, Integer, func
from sqlalchemy.orm import Mapped, mapped_column, declared_attr

class AuditMixin:
    """
    Adds standard audit columns to track creation and updates.
    """
    @declared_attr
    def created_at(cls) -> Mapped[datetime]:
        return mapped_column(
            DateTime(timezone=True), 
            server_default=func.now(), 
            nullable=False
        )

    @declared_attr
    def updated_at(cls) -> Mapped[datetime]:
        return mapped_column(
            DateTime(timezone=True), 
            server_default=func.now(), 
            onupdate=func.now(), 
            nullable=False
        )

    @declared_attr
    def created_by(cls) -> Mapped[Optional[int]]:
        # Stores the User ID of the creator. Indexed for fast lookups.
        return mapped_column(Integer, nullable=True, index=True)

    @declared_attr
    def updated_by(cls) -> Mapped[Optional[int]]:
        return mapped_column(Integer, nullable=True, index=True)


class SoftDeleteMixin:
    """
    Adds soft-delete columns so records are archived instead of permanently destroyed.
    """
    @declared_attr
    def is_deleted(cls) -> Mapped[bool]:
        return mapped_column(
            Boolean, 
            default=False, 
            server_default="false", 
            nullable=False, 
            index=True # Crucial for filtering out deleted records quickly
        )

    @declared_attr
    def deleted_at(cls) -> Mapped[Optional[datetime]]:
        return mapped_column(DateTime(timezone=True), nullable=True)

    @declared_attr
    def deleted_by(cls) -> Mapped[Optional[int]]:
        return mapped_column(Integer, nullable=True)
```

#### 2. Apply to Your Models
Now, open your core models (e.g., `backend/db/models.py` or wherever your tables are defined) and inherit from these mixins.

**Example: Updating the `Product` model**

    name: Mapped[str] = mapped_column(String(255), nullable=False)
    price: Mapped[float] = mapped_column(Numeric(10, 2), nullable=False)
    
    # created_at, updated_at, created_by, updated_by, 
    # is_deleted, deleted_at, and deleted_by are now automatically included!

### 🗄️ DOMAIN 1: Database System Management & Enterprise Scaling

#### 1. Connection Pooling Middleware (PgBouncer)
*   **The System:** A lightweight connection pooler deployed as a middleware layer between the FastAPI backend and the PostgreSQL database to manage and multiplex TCP connections.
*   **Expected Problem:** FastAPI is highly asynchronous and can spawn hundreds of concurrent requests during traffic spikes (e.g., flash sales). PostgreSQL defaults to a maximum of ~100 concurrent connections. If every API request opens a direct TCP connection, the database will rapidly run out of memory, reject new connections, and crash the entire checkout flow.
*   **The Solution:** Deploy PgBouncer in "Transaction Mode". FastAPI connects to PgBouncer instead of PostgreSQL directly. PgBouncer multiplexes thousands of incoming API requests into a small, safe, and persistent pool of 20-30 database connections, ensuring the database never exceeds its connection limits while maintaining massive throughput.

#### 2. Read/Write Splitting Architecture (CQRS Pattern)
*   **The System:** A database routing architecture that separates read operations (`SELECT`) from write operations (`INSERT`, `UPDATE`, `DELETE`) using PostgreSQL Read Replicas.
*   **Expected Problem:** E-commerce traffic is typically 80% reads (browsing products, viewing dashboards) and 20% writes (placing orders, updating inventory). During massive traffic events, heavy read traffic will lock database rows and consume CPU, preventing critical write operations like checkouts and Treasury ledger updates from completing.
*   **The Solution:** Configure a Primary DB to handle all writes (Checkout, Treasury, Inventory) and multiple Replica DBs to handle all reads (Product listings, User profiles, Admin dashboards). Implement a custom FastAPI dependency and SQLAlchemy routing logic that automatically directs `GET` requests to the replicas and `POST/PUT/DELETE` requests to the primary, ensuring browsing traffic never blocks checkout transactions.

#### 3. Declarative Table Partitioning for Massive Datasets
*   **The System:** PostgreSQL Declarative Partitioning applied to high-volume, append-only tables like `orders`, `journal_entries` (Treasury Ledger), and `audit_logs`.

*   **The Solution:** Partition massive tables by `created_at` (e.g., one partition per month). ### 🖥️ DOMAIN 2: Frontend UI Table Alignments (Enterprise Ledger UX)

#### 12. Financial Table Typographic Alignment
*   **The System:** Strict CSS and typographic rules applied to all Web Admin financial data tables (Payouts, Invoices, Treasury Ledger).
*   **Expected Problem:** Standard fonts render numbers with variable widths (e.g., a "1" takes less space than an "8"). In a financial ledger with hundreds of rows, this makes decimal points jagged, misaligned, and impossible to scan vertically, leading to severe user fatigue and financial auditing errors.
*   **The Solution:** Apply `font-variant-numeric: tabular-nums;` to all columns containing currency, amounts, or percentages to force uniform character widths. Enforce strict right-alignment for all numeric data and left-alignment for text. Ensure empty or zero values render as a perfectly aligned dash (`—`) or `0.00` rather than blank spaces.

#### 13. Expandable Workspace Table Architecture (Ghost Row)
*   **The System:** A CSS Grid and `colSpan` based architecture for the Country Ledger and complex data tables to handle inline expansion without breaking layout.
*   **Expected Problem:** Standard HTML `<table>` elements cannot easily handle a row that expands into a massive, multi-tab "Workspace" (like the Country Ledger Ghost Row or Commission Editor) without breaking the column alignment of the rows below it, resulting in a broken, unusable UI.
*   **The Solution:** Abandon strict `<table>` constraints for expandable sections. Use CSS Grid for the main table header and collapsed rows. When a row is expanded (or the Ghost Row is active), use `display: block` or `colSpan={total_columns}` to break out of the grid, rendering a full-width, padded "Workspace Card" directly beneath the trigger row while maintaining the visual flow of the ledger.

#### 14. Bulk Action Context Preservation (Sticky Headers & Columns)
*   **The System:** Implementation of sticky positioning for table headers and the primary identifier/checkbox columns in large dataset tables (Orders, Shipments, Tickets).
*   **Expected Problem:** When managing tables with 500+ rows and many columns, horizontal scrolling causes the "Checkbox" and "ID" columns to scroll off-screen. Admins lose context of which row they are selecting. Furthermore, vertical scrolling hides the column headers, forcing the user to scroll back up to remember what the data represents.
*   **The Solution:** Implement sticky positioning for the Checkbox + ID column (`left: 0`), complete with a subtle drop-shadow to act as a visual separator. Implement sticky positioning for the table header (`top: 0`). This ensures that no matter how far the Admin scrolls horizontally or vertically, the context of the row and the column definitions remain permanently visible.

#### 15. Mobile App RTL & Flexbox Logical Alignment
*   **The System:** Strict enforcement of CSS logical properties and React Native RTL (Right-to-Left) layout managers for all mobile app list and card views.
*   **Expected Problem:** The mobile app uses Flexbox to create card rows. When the app is switched to Arabic (RTL), standard `left` and `right` margins and flex directions do not automatically flip, causing text to overlap, icons to misalign, and the UI to break for GCC users.
*   **The Solution:** Audit all mobile layouts to ensure the use of the React Native RTL manager, or transition entirely to logical properties (e.g., `margin-inline-start` instead of `margin-left`, `start`/`end` instead of `left`/`right`). This guarantees that the UI perfectly mirrors itself when switching between English and Arabic without requiring duplicate layout code.

### 📸 DOMAIN 3: Media & Asset Storage Architecture

#### 16. 3-Tier Segregated Storage Architecture
*   **The System:** A strict, hierarchical folder structure for all uploaded media assets, segmented by Country, Supplier, Category, and Product.
*   **Expected Problem:** Currently, uploaded images are dumped into flat or poorly organized storage buckets. This leads to filename collisions, makes it impossible to isolate a specific supplier's assets, complicates CDN caching, and makes database migrations or supplier deletions a massive manual cleanup effort.
*   **The Solution:** Implement a 3-Tier Storage Path Architecture: `/{country_code}/{supplier_id}/{category_id}/{product_id}/`. When an image is uploaded, the Storage Service automatically routes it to this exact path. This guarantees absolute supplier isolation, prevents filename collisions, and allows for instant, bulk deletion of all assets if a product or supplier is removed from the platform.

#### 17. Automated Image Processing & Variant Generation
*   **The System:** An asynchronous background pipeline that intercepts raw image uploads, validates them, and generates multiple optimized variants.
*   **Expected Problem:** Suppliers upload massive, unoptimized raw images. Serving these directly to customers destroys mobile bandwidth, causes massive CDN egress costs, and results in agonizingly slow product page load times, directly killing conversion rates.
*   **The Solution:** Intercept the original upload and pass it through an automated processing pipeline. Validate the format and dimensions, then generate standardized variants: a Main image (1920x1080 WebP), a Gallery image, a Thumbnail (300x300 WebP), and a Small preview (150x150 WebP). Store these variants in the segregated 3-tier path and update the database to serve the exact size needed for the specific frontend view.

#### 18. Media Database Schema & Metadata Tracking
*   **The System:** A dedicated relational database table (`product_images`) to track the metadata, storage paths, and lifecycle of every uploaded asset.
*   **Expected Problem:** Storing image URLs as simple JSON arrays inside the `Product` table prevents efficient querying (e.g., "Find all products missing a main image"), makes it impossible to track who uploaded an image or when, and complicates the process of re-ordering gallery images or marking primary images.
*   **The Solution:** Create a normalized `product_images` table containing `id`, `supplier_id`, `product_id`, `country_code`, `storage_path`, `image_type` (main, gallery, thumbnail), `size_bytes`, `mime_type`, `sort_order`, and `is_primary`. This allows the frontend to efficiently query exact image variants, enables Admins to audit storage usage, and provides a clear relational link for asset management.

#### 19. Storage Security, Isolation & Orphan Cleanup
*   **The System:** Strict path-based access controls, pre-signed URL generation, and automated orphan-detection cron jobs for all media storage operations.
*   **Expected Problem:** If storage paths are predictable and lack access controls, a malicious supplier could write a script to overwrite or delete another supplier's product images. Furthermore, when products are deleted, their images are often left behind in the storage bucket, silently accumulating massive cloud storage costs over time.
*   **The Solution:** Enforce strict backend validation ensuring a supplier's API token can *only* write to or delete from their specific `/{supplier_id}/` path. For frontend viewing, generate time-limited, cryptographically signed URLs via the CDN/Storage provider. Implement automated nightly cron jobs that scan the storage bucket, compare it against the `product_images` database table, and permanently delete "orphaned" images that no longer have an active database record.

### 20. Eliminate N+1 ORM Queries via Eager Loading
*   **The System:** All SQLAlchemy queries that fetch lists of entities (Orders, Products, Suppliers) must use `selectinload()` or `joinedload()` to eagerly load related foreign-key data in a single database round-trip.
*   **Expected Problem:** If the system fetches 100 orders and then loops through them to access `order.user.name` or `order.items`, SQLAlchemy executes 101 separate database queries (1 for orders + 100 for users). Under moderate load (500 concurrent users), this will max out PostgreSQL CPU, cause connection pool exhaustion, and crash the checkout API with `500 Internal Server Error`.
*   **The Solution:** Enforce a strict code review policy and automated linter rule that flags any query accessing a relationship without eager loading. Refactor all list-based controllers to use:
    ```python
    db.query(Order).options(
        selectinload(Order.user),
        selectinload(Order.items).selectinload(Item.product)
    ).all()
    ```
    This reduces 101 queries to 1, preventing CPU spikes and ensuring sub-200ms API response times under load.

### 21. Implement Advanced Indexing Strategy (B-Tree + GIN)
*   **The System:** A comprehensive indexing plan that covers foreign keys, filtered statuses, and JSONB payload searches using both standard B-Tree and PostgreSQL-specific GIN indexes.
*   **Expected Problem:** Without proper indexes, PostgreSQL performs a "Sequential Scan" (reading every row in the table) to find data. A query for "all orders from Supplier X in status 'delivered'" on a 10-million-row `orders` table will take 30+ seconds, freezing the Admin Dashboard and causing timeout errors. Furthermore, standard B-Tree indexes cannot search *inside* JSONB columns like `payment_gateways_json`, making country configuration lookups painfully slow.
*   **The Solution:** 
    *   **B-Tree Indexes:** Add composite indexes matching actual query patterns:
        *   `CREATE INDEX ix_orders_supplier_status ON orders(supplier_id, status)`
        *   `CREATE INDEX ix_orders_created_user ON orders(created_at DESC, user_id)`
        *   `CREATE INDEX ix_products_category_active ON products(category_id, is_active)`
    *   **GIN Indexes for JSONB:** Add Generalized Inverted Indexes to enable millisecond-level searching inside JSON configurations:
        *   `CREATE INDEX idx_country_gateways ON country_configs USING GIN (payment_gateways_json)`
        *   `CREATE INDEX idx_supplier_requirements ON country_configs USING GIN (supplier_requirements_json)`
    *   **Index Cleanup:** Drop redundant single-column indexes if covered by composite indexes to reduce write overhead and storage bloat.

### 22. Tune PostgreSQL Configuration for Production Workloads
*   **The System:** Optimize `postgresql.conf` memory and connection settings to match the physical server hardware, moving beyond the default "128MB RAM" development configuration.
*   **Expected Problem:** Out-of-the-box PostgreSQL is configured for minimal resource usage. On a modern 32GB RAM server, this artificially throttles performance: complex Admin Dashboard queries with multiple JOINs spill to disk instead of using RAM, causing 5-10 second response times. Connection limits (~100 default) cause "Too Many Connections" errors during flash sales when FastAPI spawns hundreds of concurrent requests.
*   **The Solution:** Update production `postgresql.conf` or Docker environment variables with hardware-aware settings:
    *   `shared_buffers = 8GB` (25% of 32GB RAM) - Dedicated memory for caching database pages.
    *   `work_mem = 128MB` - Allows complex sorts, hashes, and JOINs to happen in RAM instead of writing temporary files to disk.
    *   `effective_cache_size = 24GB` (75% of RAM) - Tells the query planner how much OS-level caching is available, enabling better query plan selection.
    *   `max_connections = 200` - Increased limit, but paired with PgBouncer (see below) to prevent actual connection exhaustion.

### 23. Deploy PgBouncer Connection Pooling Middleware
*   **The System:** Introduce PgBouncer as a lightweight proxy between FastAPI and PostgreSQL to multiplex thousands of application requests into a small, safe pool of persistent database connections.
*   **Expected Problem:** FastAPI is asynchronous and can spawn 500+ concurrent requests during a flash sale. PostgreSQL defaults to ~100 max connections. If each request opens a direct TCP connection, the database will reject new connections with `FATAL: sorry, too many clients already`, crashing the checkout flow and losing revenue.
*   **The Solution:** Deploy PgBouncer in "Transaction Mode" via Docker. Configure FastAPI's `DATABASE_URL` to point to `postgresql://user:pass@pgbouncer:6432/db`. PgBouncer will:
    *   Accept thousands of incoming connections from FastAPI.
    *   Maintain a small pool (e.g., 20-30) of persistent connections to PostgreSQL.
    *   Multiplex requests efficiently, preventing connection exhaustion while maintaining sub-millisecond connection overhead.

### 24. Implement Read/Write Splitting via CQRS Pattern
*   **The System:** Architect the application to route read-only queries (product browsing, user profiles, admin dashboards) to PostgreSQL Read Replicas, while write operations (checkout, inventory updates, treasury entries) go to the Primary database.
*   **Expected Problem:** E-commerce traffic is typically 80% reads, 20% writes. During a flash sale, heavy read traffic (browsing products) can lock database rows and consume I/O bandwidth, preventing critical write operations (checkout, inventory deduction) from completing. This causes "inventory overselling" and lost sales.
*   **The Solution:** 
    *   Deploy 2-3 PostgreSQL Read Replicas in the same region as the Primary.
    *   Configure SQLAlchemy with multiple database binds (`primary`, `replica_1`, `replica_2`).
    *   Build a FastAPI dependency `get_db_for_read()` that routes `GET` requests to a replica, and `get_db_for_write()` that routes `POST/PUT/DELETE` to the primary.
    *   Implement a 1-2 second replication lag tolerance in the frontend (e.g., show "Order placed!" immediately, but refresh order history after a short delay to ensure replica consistency).

### 25. Implement Table Partitioning for Massive Append-Only Tables
*   **The System:** Use PostgreSQL Declarative Partitioning to split massive, append-only tables (`orders`, `journal_entries`, `audit_logs`) into monthly or yearly child tables based on the `created_at` timestamp.
*   **Expected Problem:** After 12 months of operation, the `orders` table may contain 50 million rows. Querying "Last month's revenue" requires scanning all 50 million rows, even though only 4 million belong to the target month. This causes Admin financial reports to take 30+ seconds to load, freezing the dashboard and preventing timely decision-making.
*   **The Solution:** 
    *   Convert `orders` to a partitioned table: `CREATE TABLE orders (...) PARTITION BY RANGE (created_at)`.
    *   Create monthly child tables: `orders_2026_01`, `orders_2026_02`, etc.
    *   PostgreSQL's query planner will automatically "prune" irrelevant partitions. A query for October 2026 will only scan `orders_2026_10`, reducing scan time from 30 seconds to <500ms.
    *   Implement automated partition management via a monthly cron job that creates the next month's partition and archives partitions older than 24 months to cold storage.

### 26. Offload Heavy Writes to Asynchronous Message Queues
*   **The System:** Decouple non-critical, high-latency operations (emails, push notifications, analytics aggregation) from the synchronous checkout flow using a message broker (Redis Streams or RabbitMQ) and background workers (Celery/ARQ).
*   **Expected Problem:** When a user clicks "Place Order", the system currently tries to: Create Order → Deduct Inventory → Create Treasury Journal Entry → Send Confirmation Email → Send Push Notification → Update Analytics. This synchronous chain takes 2-3 seconds, causing checkout timeouts during peak load and losing sales.
*   **The Solution:** 
    *   Keep critical, ACID-compliant operations synchronous: Create Order, Deduct Inventory, Post Treasury Journal Entry.
    *   Immediately after commit, publish a message to a queue: `{"event": "order_placed", "order_id": 123, "user_id": 456}`.
    *   Return "Success" to the user immediately (<200ms).
    *   Background workers consume the queue and handle Emails, Push Notifications, and Analytics asynchronously, with retry logic and dead-letter queue handling for failures.

### 27. Enforce Strict Migration Control via Alembic & CI/CD Gates
*   **The System:** Replace the dangerous "auto-sync on startup" hack with strict, immutable Alembic migration control, enforced by automated CI/CD checks.
*   **Expected Problem:** The current `main.py` runs `sync_sqlite_schema_with_models()` on startup, silently guessing and creating missing tables/columns. This works for local SQLite but fails catastrophically in production PostgreSQL, causing `ProgrammingError: column does not exist` crashes. Furthermore, developers can push code with new model fields but forget to write migrations, causing silent data loss or corruption.
*   **The Solution:** 
    *   **Delete the Hack:** Remove `sync_sqlite_schema_with_models()` and `_sqlite_schema_needs_upgrade()` from the startup lifecycle.
    *   **Catch Up:** Run `alembic revision --autogenerate -m "catch_up_all_orm_drift"` one final time to capture all ghost columns into proper migrations.
    *   **CI/CD Gate:** Add `alembic check` to the GitHub Actions pipeline. This command compares current ORM models against the migration history. If a developer changes a model without a corresponding migration, the pipeline fails and blocks the merge.
    *   **Local Developer Script:** Provide a `check_schema_drift.bat` script for Windows developers to run before pushing code, ensuring local schema alignment.

### 28. Standardize Schema Patterns via Reusable SQLAlchemy Mixins
*   **The System:** Create reusable `AuditMixin` and `SoftDeleteMixin` classes that automatically add `created_at`, `updated_at`, `is_deleted`, `deleted_by`, etc., to any model that inherits them.
*   **Expected Problem:** Developers manually typing audit columns on every model leads to inconsistencies: some tables have `created_at`, others don't; some use `is_deleted`, others use `status = 'archived'`. This breaks unified Admin reporting, complicates GDPR "right to be forgotten" requests, and makes soft-delete logic error-prone.
*   **The Solution:** 
    *   Create `backend/db/mixins.py` with `AuditMixin` (adds `created_at`, `updated_at`, `created_by`, `updated_by`) and `SoftDeleteMixin` (adds `is_deleted`, `deleted_at`, `deleted_by`).
    *   Update all core models (`User`, `Product`, `Order`, `Supplier`, `CountryConfig`) to inherit from these mixins.
    *   Generate an Alembic migration to backfill these columns on existing tables.
    *   Enforce via code review that all new models must inherit from these mixins, ensuring future schema consistency.

### 29. Enforce Data Integrity via Database-Level CHECK Constraints
*   **The System:** Push critical business rules down to the PostgreSQL layer using `CHECK` constraints, ensuring data validity even if application logic has bugs or is bypassed.
*   **Expected Problem:** Relying solely on FastAPI/Pydantic validation is risky. A rogue background script, direct database access, or future API version could insert negative payout amounts, 10-star ratings, or commission rates >100%, corrupting financial reports and breaking downstream calculations.
*   **The Solution:** Add SQLAlchemy `CheckConstraint` to model definitions and generate migrations:
    *   `CheckConstraint('amount >= 0', name='ck_payout_amount_non_negative')` - Prevents negative financial values.
    *   `CheckConstraint('rating >= 0 AND rating <= 5', name='ck_rating_range')` - Ensures valid product reviews.
    *   `CheckConstraint('commission_rate >= 0.0 AND commission_rate <= 1.0', name='ck_commission_pct')` - Prevents impossible commission calculations.
    *   `CheckConstraint('discount_price <= base_price', name='ck_discount_logic')` - Prevents pricing logic errors.
    *   These constraints are enforced by PostgreSQL at the storage engine level, providing a final, un-bypassable layer of data integrity.

### 30. Implement GIN Indexes for JSONB Configuration Search
*   **The System:** Apply PostgreSQL Generalized Inverted Indexes (GIN) to all `JSONB` configuration columns to enable millisecond-level searching *inside* JSON documents.
*   **Expected Problem:** The Country Ledger and Admin dashboards frequently query inside JSONB columns like `payment_gateways_json` ("find all countries where Stripe is enabled") or `supplier_requirements_json` ("find all countries requiring VAT certificates"). Without GIN indexes, PostgreSQL performs a sequential scan of every row, causing Admin searches to take 5-10 seconds and freezing the UI.
*   **The Solution:** Add GIN indexes to all JSONB configuration columns:
    *   `CREATE INDEX idx_country_gateways ON country_configs USING GIN (payment_gateways_json)`
    *   `CREATE INDEX idx_supplier_requirements ON country_configs USING GIN (supplier_requirements_json)`
    *   `CREATE INDEX idx_user_browsing ON users USING GIN (browsing_history_json)`
    *   These indexes allow PostgreSQL to search inside JSON documents as fast as standard text columns, enabling instant Admin filtering and reporting.

### 31. Bridge Operational Ledger to Double-Entry Treasury Engine
*   **The System:** Connect the existing `TransactionLedger` and `Order Settlement` operational flows to the Double-Entry `JournalEntry` system, ensuring every financial event is immutably recorded with debits and credits.
*   **Expected Problem:** The current system tracks "balances" but lacks a strict accounting framework. You cannot accurately track liabilities (supplier payouts, COD collected) vs. assets, making VAT remittance, multi-currency reconciliation, and financial audits impossible. Manual spreadsheet reconciliation becomes the only way to verify financial truth.
*   **The Solution:** 
    *   Build the `TreasuryService.post_journal_entry()` function that enforces `Sum(Debits) == Sum(Credits)` with row-level database locking.
    *   Inject Treasury triggers into critical business flows:
        *   *Order Delivered:* Debit `Deferred Revenue`, Credit `Supplier Payable`, `Logistics Payable`, `Commission Revenue`, `VAT Payable`.
        *   *Payment Webhook Verified:* Debit `Gateway Clearing`, Credit `Deferred Revenue`.
        *   *Payout Dispatched:* Debit `Supplier Payable`, Credit `Cash Operating`.
    *   Build the Finance Command Center UI to read directly from `AccountBalance` materialized views, providing real-time Cash Position, Liabilities, and Equity reporting.

### 32. Implement Redis Caching Layer for Heavy Analytical Queries
*   **The System:** Use Redis to cache the results of heavy, read-mostly analytical queries (Country-wise Sales, Category Trends, Most Searched Keywords) with a 5-minute TTL.
*   **Expected Problem:** The Operations Command Center displays 30+ complex metrics. If each metric triggers a fresh database query with multiple JOINs and aggregations, the dashboard will take 10+ seconds to load, causing Admin frustration and preventing real-time decision-making.
*   **The Solution:** 
    *   Build a background cron job that runs every 5 minutes, calculates heavy aggregates (Country Sales, Category Trends, Search Logs), and stores the JSON result in Redis with a key like `dashboard:analytics:country_sales:OM`.
    *   The Command Center frontend reads directly from Redis (`GET dashboard:analytics:country_sales:OM`), which takes <5ms, ensuring sub-500ms dashboard load times.
    *   Implement cache invalidation: When a new order is placed in Oman, invalidate the `country_sales:OM` cache key so the next read triggers a fresh calculation.

### 33. Implement Row-Level Security (RLS) via SQLAlchemy ORM Interception
*   **The System:** Enforce country-level data isolation at the ORM layer, ensuring `country_manager` and `country_head` roles can only query data belonging to their assigned countries, regardless of API endpoint or manual URL manipulation.
*   **Expected Problem:** Basic RBAC checks in controllers are error-prone. A developer might forget to add `.filter(country_code == user_country)` to a new query, allowing a Country Manager for Oman to accidentally (or maliciously) access Saudi Arabia's supplier payout data via direct ID enumeration (`/api/payouts/105` instead of `/api/payouts/104`).
*   **The Solution:** 
    *   Build a FastAPI dependency `get_country_scope()` that reads the user's JWT, queries a Redis cache for their `assigned_countries`, and attaches the scope to the Request State.
    *   Register a SQLAlchemy `before_compile` event listener that intercepts all queries against "Country-Aware" models (`Order`, `Supplier`, `Payout`).
    *   The listener automatically injects `WHERE country_code IN (:assigned_countries)` into the SQL, making data isolation mathematically enforced at the ORM level. Developers cannot forget this filter—it is applied universally.

### 34. Implement Immutable Audit Logging via Append-Only Tables
*   **The System:** Create append-only, cryptographically sealed database tables for `security_audit_logs` and `financial_audit_logs` that physically block `UPDATE` and `DELETE` operations.
*   **Expected Problem:** If a rogue Database Administrator or compromised application account gains write access, they could delete or alter audit logs to cover up fraud, data breaches, or compliance violations. Standard logging to files or mutable tables provides no forensic integrity.
*   **The Solution:** 
    *   Create `security_audit_logs` and `financial_audit_logs` tables with database-level triggers that raise an exception on any `UPDATE` or `DELETE` attempt.
    *   Write logs with a cryptographic hash chain: each log entry includes a hash of the previous entry's content, creating an immutable chain. Tampering with any entry breaks the chain and is instantly detectable.
    *   Archive logs to write-once, read-many (WORM) storage (e.g., AWS S3 Object Lock) for long-term compliance retention.
    *   This ensures that even with full database access, no actor can alter the historical record of financial or security events.
